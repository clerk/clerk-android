# Biometric credential storage contract (Android, v2)

This document specifies how Clerk biometric credentials ("trusted devices") are stored on an
Android device. Contract v2 (sections 1–6 and 8) is normative for every Clerk SDK. Contract v1
(section 7) is the format `clerk-android` used before v2; it is now legacy, read only by
`clerk-android` to migrate it to v2.

Every Clerk SDK that runs inside the same Android app (for example `clerk-android`'s prebuilt
`AuthView`/`UserProfileView` alongside `@clerk/expo-biometrics`) shares one Clerk client. The
Frontend API allows one active biometric credential per client, platform and app identifier, so
enrolling in one SDK revokes the credential enrolled by another. To avoid that, all SDKs must read
and write the same keys and metadata described here.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

The pinned identifiers are covered by
`source/api/src/test/java/com/clerk/api/biometriccredential/BiometricCredentialStorageContractTest.kt`
and the fixtures in `source/api/src/test/resources/biometric-credential-storage/`.

## 1. Identifiers at a glance

| What                          | Value                                                             |
| ----------------------------- | ----------------------------------------------------------------- |
| Contract version              | `2` (file name suffix `.v2.json` and top-level `"version": 2`)    |
| Store directory               | `<Context.getNoBackupFilesDir()>/clerk/`                          |
| Metadata file                 | `clerk/biometric_credentials.v2.json` (UTF-8 JSON, plaintext)     |
| Temporary file                | `clerk/biometric_credentials.v2.json.tmp`                         |
| Lock file                     | `clerk/biometric_credentials.lock`                                |
| Identifier hint encoding      | lowercase hex SHA-256 of the normalized hint                      |
| Keystore provider             | `AndroidKeyStore`                                                 |
| Signing key alias             | `com.clerk.trusted_device.<local_key_id>`                         |
| Local key ID (as generated)   | `tdlk_` + 32 lowercase hex characters                             |
| Signature algorithm           | `SHA256withECDSA` on `secp256r1`, sent as `ES256`                 |
| Frontend API `platform`       | `android`                                                         |
| Frontend API `app_identifier` | `Context.getPackageName()` of the host app                        |

v2 shares nothing with the storage of the device token or any other SDK state: no
`SharedPreferences` file and no encryption key. Metadata is not secret (it holds IDs, timestamps
and a hash, never a raw identifier); the private keys it points to stay in the Keystore.

## 2. Signing key (Android Keystore)

One EC key pair exists per enrolled credential. The private key never leaves the Keystore.

- Provider: `AndroidKeyStore`.
- Alias: `com.clerk.trusted_device.` followed by the record's `local_key_id`, byte for byte.
  Readers MUST treat `local_key_id` as opaque and only concatenate it with the prefix.
- `local_key_id` as generated by `clerk-android`: `tdlk_` followed by a random UUID's 32 lowercase
  hex digits with no dashes. Other writers SHOULD use the same shape; readers MUST NOT rely on it.
- Minimum API level: 28 (Android 9). Enrollment and signing fail below that.

`KeyGenParameterSpec`:

| Parameter                             | Value                                                                                   |
| ------------------------------------- | --------------------------------------------------------------------------------------- |
| Algorithm                             | `KeyProperties.KEY_ALGORITHM_EC`                                                        |
| `setAlgorithmParameterSpec`           | `ECGenParameterSpec("secp256r1")`                                                       |
| Purposes                              | `PURPOSE_SIGN` only                                                                     |
| `setDigests`                          | `DIGEST_SHA256` only                                                                    |
| `setUserAuthenticationRequired`       | `true`                                                                                  |
| API 30+                               | `setUserAuthenticationParameters(0, <authenticators>)` (auth required for every use)     |
| API 28–29                             | `setUserAuthenticationValidityDurationSeconds(-1)` (auth required for every use)        |
| `setInvalidatedByBiometricEnrollment` | `true` for `biometry_current_set`, `false` otherwise                                    |

Nothing else is set (no StrongBox request, attestation challenge or unlocked-device requirement).

Per policy:

| Policy                        | Key authenticators (API 30+)                  | Key on API 28–29 | Invalidated by enrollment change |
| ----------------------------- | --------------------------------------------- | ---------------- | -------------------------------- |
| `biometry_current_set`        | `AUTH_BIOMETRIC_STRONG`                       | biometric only   | yes                              |
| `biometry_any`                | `AUTH_BIOMETRIC_STRONG`                       | biometric only   | no                               |
| `biometry_or_device_passcode` | `AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL` | biometric only   | no                               |

`BiometricPrompt` (`android.hardware.biometrics.BiometricPrompt`) is shown with a
`CryptoObject(Signature)`. On API 30+ `biometry_or_device_passcode` allows
`BIOMETRIC_STRONG or DEVICE_CREDENTIAL` with no negative button; every other case uses
`BIOMETRIC_STRONG` (set explicitly on API 30+) with a negative "Cancel" button.

A policy is considered usable when API ≥ 28 and
`androidx.biometric.BiometricManager.canAuthenticate(...) == BIOMETRIC_SUCCESS` for
`BIOMETRIC_STRONG`, or `BIOMETRIC_STRONG or DEVICE_CREDENTIAL` for `biometry_or_device_passcode` on
API 30+.

Keys created for `biometry_or_device_passcode` on API 28–29 remain biometric-only after an OS
upgrade, because key protections cannot change after creation.


## 3. Metadata storage

### 3.1 Location

- Directory: `clerk` inside `Context.getNoBackupFilesDir()` of the host app. Create it (with
  parents) when missing. `noBackupFilesDir` is excluded from Auto Backup and device transfer, so
  records are never restored onto a device that lacks their Keystore keys.
- Metadata file: `biometric_credentials.v2.json` in that directory. A missing file is an empty
  store.
- The file is only ever replaced through the write protocol in section 4. Implementations MUST NOT
  delete it; an empty store is written as empty arrays.

### 3.2 File format

UTF-8 JSON object. Fixture:
`source/api/src/test/resources/biometric-credential-storage/v2/biometric_credentials.v2.json`.

```json
{
  "version": 2,
  "credentials": [
    {
      "id": "td_...",
      "local_key_id": "tdlk_0123456789abcdef0123456789abcdef",
      "user_id": "user_...",
      "app_identifier": "com.example.app",
      "identifier_hint_sha256": "b4c9a289323b21a01c3e940f150eb9b8c542587f1abfd8f0e1cc1ffc5e475514",
      "policy": "biometry_current_set",
      "created_at": 1735689600000,
      "updated_at": 1735689600001
    }
  ],
  "pending_cleanup_user_ids": ["user_..."]
}
```

| Top-level key              | Type             | Meaning                                                           |
| -------------------------- | ---------------- | ----------------------------------------------------------------- |
| `version`                  | integer          | MUST be `2`.                                                      |
| `credentials`              | array            | Credential records (3.3). Order is not significant.               |
| `pending_cleanup_user_ids` | array of strings | Users whose local credentials still need removing (3.5).          |

- If `version` is not the integer `2`, the file belongs to an incompatible contract: readers MUST
  treat the store as empty and writers MUST NOT modify it (fail the write instead). Additive changes
  (new fields, new policies, new top-level keys) keep `version` at `2`; see 3.4.
- If the file is not a JSON object, readers treat the store as empty and the next write replaces
  it.
- A missing or non-array `credentials` / `pending_cleanup_user_ids` reads as empty.
- Writers always write all three keys. `clerk-android` writes compact JSON with the known keys
  first; readers MUST NOT depend on key order or whitespace.

### 3.3 Credential records

| Field                    | Type            | Required | Meaning                                                                           |
| ------------------------ | --------------- | -------- | --------------------------------------------------------------------------------- |
| `id`                     | string          | yes      | Server-side biometric credential ID. Unique within `credentials`.                 |
| `local_key_id`           | string          | yes      | Keystore alias suffix (see section 2).                                            |
| `user_id`                | string          | yes      | ID of the user the credential belongs to.                                         |
| `app_identifier`         | string          | yes      | App identifier returned by the server at enrollment; equals the package name.     |
| `identifier_hint_sha256` | string or null  | no       | Hash of the local-only identifier hint (3.6). Omitted or `null` when there is none. |
| `policy`                 | string          | yes      | `biometry_current_set`, `biometry_any` or `biometry_or_device_passcode`.          |
| `created_at`             | integer (int64) | yes      | Server `created_at`, milliseconds since the Unix epoch.                           |
| `updated_at`             | integer (int64) | yes      | Server `updated_at`, milliseconds since the Unix epoch.                           |

- Field names are snake_case. Strings are JSON strings and timestamps JSON integers; any other type
  makes the record undecodable.
- `policy` MUST always be written. Unlike v1 there is no default: a missing, `null` or
  unrecognized `policy` makes the record unusable for this reader.
- `clerk-android` omits `identifier_hint_sha256` when there is no hint. Readers MUST accept a
  missing key and `null` alike.

### 3.4 Forward compatibility

Readers MUST NOT lose data they do not understand:

- A record that cannot be decoded (not an object, a missing or mistyped required field) or whose
  `policy` is unknown is skipped for selection (section 5) and kept unchanged (as a JSON value) on
  every rewrite. It is never coerced to a known policy.
- When replacing a record, writers MUST keep every field of the existing record that they do not
  write themselves.
- Writers MUST keep top-level keys they do not know.
- Records are removed only by `id` (string equality), which applies to undecodable records with a
  string `id` too.

### 3.5 Pending cleanup queue

`pending_cleanup_user_ids` lists users whose account was deleted on this device and whose local
credentials still need removing. Entries are non-blank strings, written sorted (by UTF-16 code
unit, as `String.compareTo`) and de-duplicated; non-string and blank entries are dropped on
rewrite.

When the prebuilt UI deletes an account it adds the user ID, removes that user's records and keys
for the current app, then removes the ID. On every `Clerk.initialize`, `clerk-android` retries the
removal for each queued ID and drops the ID once it succeeds. If a key or record cannot be deleted
the ID stays queued. Other SDKs SHOULD process the queue the same way, or at least leave it
untouched.

### 3.6 Identifier hints

The raw identifier hint (for example an email address) is never stored. Writers store
`identifier_hint_sha256`:

1. Normalize the hint: remove leading and trailing whitespace, then lowercase it without locale
   rules (Kotlin `trim().lowercase()`, Java `trim()`-equivalent plus `toLowerCase(Locale.ROOT)`).
2. If the result is empty, there is no hint: omit the field.
3. Otherwise store the SHA-256 of the result's UTF-8 bytes as 64 lowercase hex characters.

Test vector: `"  User@Example.COM\n"` → `b4c9a289323b21a01c3e940f150eb9b8c542587f1abfd8f0e1cc1ffc5e475514`.

To match a hint at sign-in, compute the same hash and compare for equality. The hint is only used
to choose between local records; it is not a secret and the hash is not a security boundary.

## 4. Write protocol

All SDKs MUST follow this protocol for every change to the metadata file, so concurrent writers in
the same process or in different processes never lose an update.

### 4.1 Lock

- Lock file: `biometric_credentials.lock` in the store directory. Create it if missing (open with
  `RandomAccessFile(file, "rw")`). Its contents are ignored; never delete it.
- Every read-modify-write MUST hold an exclusive lock on the whole lock file, taken with
  `FileChannel.tryLock()` (or `lock()`), i.e. a POSIX `fcntl` record lock on Android.
- Java reports a lock already held by another channel in the same process (another SDK) as
  `OverlappingFileLockException` instead of blocking, and `tryLock()` returns `null` while another
  process holds it. In both cases retry with a short backoff. `clerk-android` starts at 2 ms,
  doubles up to 50 ms, and gives up after 5 s by failing the operation.
- Implementations SHOULD also serialize their own threads with an in-process mutex before taking
  the file lock, so their own threads do not spin on `OverlappingFileLockException`.
- Keep the lock file's channel open for the life of the process. POSIX locks belong to the
  process, and closing any descriptor of the file can release a lock that another SDK in the same
  process holds.
- Hold the lock only for the read-modify-write below. Never call back into another SDK, show UI or
  make network requests while holding it, and never take it recursively.

### 4.2 Read-modify-write

While holding the lock:

1. Read and parse the metadata file (section 3). If `version` is not `2`, release the lock and fail.
2. Apply the change to the parsed JSON, preserving everything required by 3.4.
3. Write the result atomically:
   1. Write the complete UTF-8 JSON to `biometric_credentials.v2.json.tmp` in the same directory,
      truncating any existing temporary file.
   2. Flush and `fsync` it (`FileOutputStream.getFD().sync()`), then close it.
   3. `rename(2)` it over `biometric_credentials.v2.json` (`File.renameTo`; fail if it returns
      `false`).
   4. SHOULD `fsync` the directory (`clerk-android` does so on a best-effort basis).
4. Release the lock.

If any step fails, the operation fails and the previous file stays intact. A leftover temporary
file is ignored by readers and overwritten by the next writer.

### 4.3 Reads

A reader that does not modify the file MAY read it without the lock: the atomic rename guarantees
it sees either the previous or the next complete file. Readers MUST treat a missing file as an
empty store.

## 5. Behavior rules

### 5.1 Selecting a credential

1. Biometric sign-in must be available in the Clerk environment (environment loaded, Native API
   enabled, biometric sign-in enabled).
2. Consider only decodable records with a known `policy` (3.4) whose `app_identifier` equals the
   host app's package name.
3. If a credential ID was requested, keep only that `id`.
4. If selecting for the signed-in user, keep that `user_id`. Otherwise, if an identifier hint was
   given, keep records whose `identifier_hint_sha256` equals the hint's hash (3.6). A missing or
   blank hint keeps all records.
5. Sort by `created_at` descending, then `updated_at` descending, then `id` descending.
6. Drop any record whose Keystore alias does not exist, and delete that record.
7. Skip (but keep) records whose `policy` is not currently usable on the device.
8. With an active session, reconcile against the server's credential list for the signed-in user:
   records for other users are selectable as-is; for the signed-in user, delete records whose
   credential is missing on the server or not `active`, and select the first remaining one. If the
   list request fails, select the first record without reconciling.

Session reverification uses the first candidate for the session's user with
`policy == biometry_current_set`. If there is none it fails with
`biometric_credential_policy_incompatible`.

### 5.2 Deleting local credentials

"Delete a local credential" means delete the Keystore alias, then remove the record (section 4).
It is local only: the server credential is not revoked. This happens when:

- `Signature.initSign` throws `KeyPermanentlyInvalidatedException` (for example biometrics changed
  on a `biometry_current_set` key), or the alias has no key.
- The server rejects a sign-in or reverification with `form_resource_not_found` or
  `trusted_device_not_registered` and `meta.param_name == "trusted_device_id"`, or the validation
  endpoint reports the credential invalid.
- Reconciliation finds the credential missing or not `active` (5.1 step 8).
- A credential is revoked through the SDK (after the server revoke succeeds).

### 5.3 Enrollment

1. Generate a new key (section 2) for the chosen policy. `clerk-android` defaults to
   `biometry_current_set`.
2. Prepare enrollment with `platform=android`, `app_identifier=<package name>`,
   `algorithm=ES256` and `public_key_jwk`, then sign the returned `client_data` (section 6) and
   attempt enrollment with `client_data` and `signature`.
3. If any step fails, delete the new key.
4. On success, save a record: `id`, `app_identifier`, `created_at` and `updated_at` from the server
   response, plus `local_key_id`, `user_id`, `identifier_hint_sha256` and `policy`. Saving replaces
   any record with the same `id`.
5. If saving fails for any reason (including a lock timeout or an unsupported file version),
   revoke the new credential on the server, delete the new key and fail the enrollment.
6. Then delete every other local credential for the same `app_identifier` and `user_id`
   (best-effort), since the server keeps only one active credential for this client and app.
   Records for other users are left for reconciliation (5.1 step 8).

## 6. Signing format

- Sign the exact `client_data` string returned by the server, as UTF-8 bytes, with
  `SHA256withECDSA`. Do not decode or re-serialize it.
- Convert the DER signature to raw `r || s`: each integer is stripped of leading zero bytes and
  left-padded to 32 bytes, giving 64 bytes.
- Encode with unpadded base64url (`Base64.URL_SAFE | NO_PADDING | NO_WRAP`).
- Send `algorithm=ES256` alongside it.

Public key JWK sent at enrollment (coordinates are 32-byte big-endian, unpadded base64url):

```json
{"kty":"EC","crv":"P-256","x":"<x>","y":"<y>","alg":"ES256"}
```


## 7. Legacy contract v1 (read-only)

`clerk-android` stored metadata this way before v2. Other SDKs MUST NOT read, write or remove v1
data, and MUST NOT use the `clerk_preferences.master_key` Keystore key. Only `clerk-android`
reads v1, to migrate it. Fixtures: `source/api/src/test/resources/biometric-credential-storage/v1/`.

### 7.1 v1 format

- `SharedPreferences` file `clerk_preferences` (`Context.MODE_PRIVATE`), string preferences
  `TRUSTED_DEVICE_CREDENTIALS` (JSON array of records) and
  `PENDING_TRUSTED_DEVICE_CREDENTIAL_CLEANUP` (JSON array of user ID strings).
- Each value is `clerk:v1:<base64(iv)>:<base64(ciphertext || tag)>`, `AES/GCM/NoPadding` with a
  128-bit tag and no AAD, keyed by the Keystore AES key `clerk_preferences.master_key`. The same key
  encrypts `DEVICE_TOKEN` and other `clerk-android` state.
- Records use the v2 field names except that they hold the raw normalized hint in
  `identifier_hint` instead of `identifier_hint_sha256`, and `policy` may be omitted. A missing,
  `null` or unrecognized v1 `policy` means `biometry_or_device_passcode`. Unknown fields were
  dropped on rewrite; undecodable records were dropped.

### 7.2 Migration to v2

`clerk-android` migrates once per process, on the first access to the store, while holding the v2
lock (section 4.1):

1. Load and decrypt both v1 preferences through its encrypted storage. If neither exists, there is
   nothing to migrate.
2. Decode the v1 records with the v1 rules above (dropping undecodable ones) and convert each:
   `identifier_hint` becomes `identifier_hint_sha256` (3.6), and `policy` is written explicitly
   (the v1 default becomes `biometry_or_device_passcode`). Other v1 fields are not carried over;
   the raw hint is never written to v2.
3. Merge by `id`: v1 records whose `id` already exists in v2 are ignored (v2 wins); others are
   appended. Union the pending cleanup IDs.
4. Write the v2 file (4.2 step 3).
5. Only then delete both v1 preferences.

The migration is idempotent and crash-safe: if the process dies between steps 4 and 5, the next
run merges the same records by `id` again without duplicating them, then deletes v1. Keystore
signing keys (`com.clerk.trusted_device.<local_key_id>`) are not touched, so migrated records keep
working. If the Keystore is unavailable the v1 values cannot be read and migration is retried in a
later process. v1 values that fail to decrypt are deleted, as v1 always did.

## 8. Compatibility rules

- Any SDK that stores biometric credentials inside an app that may also contain `clerk-android`
  MUST use the identifiers, file format and write protocol in this document.
- Records and keys are shared. An SDK may use, replace or delete a credential that another SDK
  enrolled, following the rules in section 5.
- Adding a record field, a policy value or a top-level key is backwards compatible: v2 readers
  preserve what they do not understand (3.4) and skip unknown policies.
- Changing an identifier, the meaning of an existing field or the write protocol requires a new
  contract version, with a new file name and `version` value, and a migration from v2.

## 9. Known limitations

- **Downgrades.** A `clerk-android` release older than v2 only reads v1, which has been deleted
  after migration. Downgrading the SDK loses local enrollments (the Keystore keys remain but are
  unreferenced); users can enroll again.
- **Resurrected records after an interrupted migration.** If another SDK deletes a migrated record
  between steps 4 and 5 of 7.2 and the process dies in that window, the next migration re-adds it.
  Selection then removes it again (missing key, or reconciliation with the server).
- **Undecodable records are never cleaned up** by an SDK that cannot decode them, including during
  account-deletion cleanup, because it cannot tell whose they are.
- **No lock on reads.** Readers see a consistent snapshot but may act on it after another SDK has
  changed the file; deletes and saves are by `id`, so this cannot drop another SDK's record.
- **Hint normalization** relies on each SDK trimming and lowercasing identically. SDKs SHOULD pass
  hints that are already trimmed so differences in Unicode whitespace handling cannot matter.
- **Test coverage.** Robolectric has no `AndroidKeyStore`. The contract test installs an in-memory
  `AndroidKeyStore` JCA provider for the v1 migration path, so actual Keystore hardware behavior is
  not exercised. Lock tests run on the host JVM's `fcntl` implementation, not Android's.
