# Biometric credential storage contract (Android, v1)

This document specifies how Clerk biometric credentials ("trusted devices") are stored on an
Android device. It describes the format `clerk-android` has shipped since biometric sign-in was
introduced; nothing here changes that behavior.

Every Clerk SDK that runs inside the same Android app (for example `clerk-android`'s prebuilt
`AuthView`/`UserProfileView` alongside `@clerk/expo-biometrics`) shares one Clerk client. The
Frontend API allows one active biometric credential per client, platform and app identifier, so
enrolling in one SDK revokes the credential enrolled by another. To avoid that, all SDKs must read
and write the same keys and metadata described here.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

The pinned identifiers are covered by
`source/api/src/test/java/com/clerk/api/biometriccredential/BiometricCredentialStorageContractTest.kt`
and the fixtures in `source/api/src/test/resources/biometric-credential-storage/v1/`.

## 1. Identifiers at a glance

| What                          | Value                                                         |
| ----------------------------- | ------------------------------------------------------------- |
| Contract version              | `1` (encoded in the value prefix `clerk:v1:`)                 |
| Keystore provider             | `AndroidKeyStore`                                             |
| Signing key alias             | `com.clerk.trusted_device.<local_key_id>`                     |
| Local key ID (as generated)   | `tdlk_` + 32 lowercase hex characters                         |
| SharedPreferences file        | `clerk_preferences` (`Context.MODE_PRIVATE`)                  |
| Credential metadata key       | `TRUSTED_DEVICE_CREDENTIALS`                                  |
| Pending cleanup key           | `PENDING_TRUSTED_DEVICE_CREDENTIAL_CLEANUP`                   |
| Value encryption key alias    | `clerk_preferences.master_key`                                |
| Encrypted value prefix        | `clerk:v1:`                                                   |
| Value cipher                  | `AES/GCM/NoPadding`, 128-bit tag, no AAD                      |
| Signature algorithm           | `SHA256withECDSA` on `secp256r1`, sent as `ES256`             |
| Frontend API `platform`       | `android`                                                     |
| Frontend API `app_identifier` | `Context.getPackageName()` of the host app                    |

## 2. Signing key (Android Keystore)

One EC key pair exists per enrolled credential. The private key never leaves the Keystore.

- Provider: `AndroidKeyStore`.
- Alias: `com.clerk.trusted_device.` followed by the record's `local_key_id`, byte for byte.
  Readers MUST treat `local_key_id` as opaque and only concatenate it with the prefix.
- `local_key_id` as generated by `clerk-android`: `tdlk_` followed by a random UUID's 32 lowercase
  hex digits with no dashes. Other writers SHOULD use the same shape; readers MUST NOT rely on it.
- Minimum API level: 28 (Android 9). Enrollment and signing fail below that.

`KeyGenParameterSpec`:

| Parameter                             | Value                                                                                   |
| ------------------------------------- | --------------------------------------------------------------------------------------- |
| Algorithm                             | `KeyProperties.KEY_ALGORITHM_EC`                                                        |
| `setAlgorithmParameterSpec`           | `ECGenParameterSpec("secp256r1")`                                                       |
| Purposes                              | `PURPOSE_SIGN` only                                                                     |
| `setDigests`                          | `DIGEST_SHA256` only                                                                    |
| `setUserAuthenticationRequired`       | `true`                                                                                  |
| API 30+                               | `setUserAuthenticationParameters(0, <authenticators>)` (auth required for every use)     |
| API 28–29                             | `setUserAuthenticationValidityDurationSeconds(-1)` (auth required for every use)        |
| `setInvalidatedByBiometricEnrollment` | `true` for `biometry_current_set`, `false` otherwise                                    |

Nothing else is set (no StrongBox request, attestation challenge or unlocked-device requirement).

Per policy:

| Policy                        | Key authenticators (API 30+)                  | Key on API 28–29 | Invalidated by enrollment change |
| ----------------------------- | --------------------------------------------- | ---------------- | -------------------------------- |
| `biometry_current_set`        | `AUTH_BIOMETRIC_STRONG`                       | biometric only   | yes                              |
| `biometry_any`                | `AUTH_BIOMETRIC_STRONG`                       | biometric only   | no                               |
| `biometry_or_device_passcode` | `AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL` | biometric only   | no                               |

`BiometricPrompt` (`android.hardware.biometrics.BiometricPrompt`) is shown with a
`CryptoObject(Signature)`. On API 30+ `biometry_or_device_passcode` allows
`BIOMETRIC_STRONG or DEVICE_CREDENTIAL` with no negative button; every other case uses
`BIOMETRIC_STRONG` (set explicitly on API 30+) with a negative "Cancel" button.

A policy is considered usable when API ≥ 28 and
`androidx.biometric.BiometricManager.canAuthenticate(...) == BIOMETRIC_SUCCESS` for
`BIOMETRIC_STRONG`, or `BIOMETRIC_STRONG or DEVICE_CREDENTIAL` for `biometry_or_device_passcode` on
API 30+.

Keys created for `biometry_or_device_passcode` on API 28–29 remain biometric-only after an OS
upgrade, because key protections cannot change after creation.

## 3. Metadata storage

### 3.1 Location

- `SharedPreferences` file `clerk_preferences`, opened with `Context.MODE_PRIVATE`.
- Credential records: string preference `TRUSTED_DEVICE_CREDENTIALS`.
- Pending cleanup queue: string preference `PENDING_TRUSTED_DEVICE_CREDENTIAL_CLEANUP`.
- Writes use `commit()` (synchronous).
- When a list becomes empty the preference is removed, not written as `[]`.

The same file holds other `clerk-android` state (`DEVICE_TOKEN`, `DEVICE_ID`,
`CACHED_CLERK_STATE`, `SHARED_SESSION_SYNC_SNAPSHOT`, `PENDING_NATIVE_MAGIC_LINK_FLOW`) encrypted
with the same key. Other SDKs MUST NOT read, write or remove any preference other than the two
listed above.

### 3.2 Value encryption

Every value is stored as:

```
clerk:v1:<base64(iv)>:<base64(ciphertext || tag)>
```

- `clerk:v1:` is a literal ASCII prefix.
- `:` separates the IV from the sealed bytes. Split on the first `:` after the prefix.
- Base64 is the standard alphabet (`+`, `/`) with `=` padding and no line breaks
  (`android.util.Base64.NO_WRAP`, equivalent to `java.util.Base64.getEncoder()`).
- Cipher: `AES/GCM/NoPadding`, 128-bit authentication tag appended to the ciphertext (the JCA
  default layout), no additional authenticated data.
- IV: generated by the Keystore on encryption (randomized encryption is required, so callers cannot
  supply one). It is 12 bytes in practice; readers MUST use the decoded IV length rather than assume
  it.
- Plaintext: UTF-8 JSON (see 3.3 and 3.4).

Key: Android Keystore secret key with alias `clerk_preferences.master_key`. When the alias does not
exist, `clerk-android` generates it lazily on first use with:

```kotlin
KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore").init(
  KeyGenParameterSpec.Builder(
      "clerk_preferences.master_key",
      KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT,
    )
    .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
    .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
    .setRandomizedEncryptionRequired(true)
    .setUserAuthenticationRequired(false)
    .build() // no setKeySize: Keystore default (128-bit AES)
)
```

An SDK that needs to write before the key exists MUST generate it with exactly these parameters,
and MUST NOT delete, replace or regenerate the key when it already exists.

Reader behavior in `clerk-android` that other writers must account for:

- A value that fails to decrypt (wrong key, bad format, bad tag) is **deleted** from preferences
  and read as absent.
- A value without the `clerk:v1:` prefix is treated as legacy plaintext, returned as-is and
  rewritten encrypted. Writers MUST always write the encrypted form.
- If the Keystore is unavailable, `clerk-android` neither reads nor writes these values.

### 3.3 `TRUSTED_DEVICE_CREDENTIALS` plaintext

A JSON array of credential records, in insertion order. Fixture:
`source/api/src/test/resources/biometric-credential-storage/v1/trusted_device_credentials.json`.

| Field             | Type                | Required | Meaning                                                                                                   |
| ----------------- | ------------------- | -------- | --------------------------------------------------------------------------------------------------------- |
| `id`              | string              | yes      | Server-side biometric credential ID.                                                                      |
| `local_key_id`    | string              | yes      | Keystore alias suffix (see section 2).                                                                    |
| `user_id`         | string              | yes      | ID of the user the credential belongs to.                                                                 |
| `app_identifier`  | string              | yes      | App identifier returned by the server at enrollment; equals the host app's package name.                  |
| `identifier_hint` | string              | no       | Local-only hint to pick a credential at sign-in, normalized by trimming and lowercasing; omitted if none. |
| `policy`          | string              | no       | `biometry_current_set`, `biometry_any` or `biometry_or_device_passcode`. See below.                       |
| `created_at`      | integer (int64)     | yes      | Server `created_at`, milliseconds since the Unix epoch.                                                   |
| `updated_at`      | integer (int64)     | yes      | Server `updated_at`, milliseconds since the Unix epoch.                                                   |

Field names are snake_case. Records using camelCase names are rejected.

`policy` rules:

- `clerk-android` omits `policy` when it is `biometry_or_device_passcode`, and omits
  `identifier_hint` when it is null. Other writers MAY write either field explicitly
  (including `null`).
- A missing, `null` or unrecognized `policy` reads as `biometry_or_device_passcode`. Older SDKs did
  not write the field for their default, and metadata cannot strengthen a key that already exists.

Decoding rules in `clerk-android`:

- Unknown fields are ignored and are **not preserved**: every write re-encodes all records from
  the decoded model.
- A record that fails to decode (for example a missing required field) is dropped and disappears
  on the next write.
- If the whole value is not a JSON array, the preference is removed.
- Every change is a read-modify-write of the whole array. Saving a record replaces any record with
  the same `id`.

### 3.4 `PENDING_TRUSTED_DEVICE_CREDENTIAL_CLEANUP` plaintext

A JSON array of user ID strings, written sorted and de-duplicated; blank entries are ignored.
Fixture: `pending_trusted_device_credential_cleanup.json`.

Each entry is a user whose account was deleted on this device and whose local credentials still
need removing. When the prebuilt UI deletes an account it adds the user ID, removes that user's
records and keys for the current app, then removes the ID. On every `Clerk.initialize`,
`clerk-android` retries the removal for each queued ID and drops the ID once it succeeds. If a
key cannot be deleted the ID stays queued. Other SDKs SHOULD process the queue the same way, or at
least leave it untouched.

## 4. Behavior rules

### 4.1 Selecting a credential

1. Biometric sign-in must be available in the Clerk environment (environment loaded, Native API
   enabled, biometric sign-in enabled).
2. Keep records whose `app_identifier` equals the host app's package name.
3. If a credential ID was requested, keep only that `id`.
4. If selecting for the signed-in user, keep that `user_id`. Otherwise, if an identifier hint was
   given, normalize it (trim, lowercase) and keep records whose `identifier_hint` equals it. A
   missing or blank hint keeps all records.
5. Sort by `created_at` descending, then `updated_at` descending, then `id` descending.
6. Drop any record whose Keystore alias does not exist, and delete that record.
7. Skip (but keep) records whose `policy` is not currently usable on the device.
8. With an active session, reconcile against the server's credential list for the signed-in user:
   records for other users are selectable as-is; for the signed-in user, delete records whose
   credential is missing on the server or not `active`, and select the first remaining one. If the
   list request fails, select the first record without reconciling.

Session reverification uses the first candidate for the session's user with
`policy == biometry_current_set`. If there is none it fails with
`biometric_credential_policy_incompatible`.

### 4.2 Deleting local credentials

"Delete a local credential" means delete the Keystore alias, then remove the record. It is local
only: the server credential is not revoked. This happens when:

- `Signature.initSign` throws `KeyPermanentlyInvalidatedException` (for example biometrics changed
  on a `biometry_current_set` key), or the alias has no key.
- The server rejects a sign-in or reverification with `form_resource_not_found` or
  `trusted_device_not_registered` and `meta.param_name == "trusted_device_id"`, or the validation
  endpoint reports the credential invalid.
- Reconciliation finds the credential missing or not `active` (4.1 step 8).
- A credential is revoked through the SDK (after the server revoke succeeds).

### 4.3 Enrollment

1. Generate a new key (section 2) for the chosen policy. `clerk-android` defaults to
   `biometry_current_set`.
2. Prepare enrollment with `platform=android`, `app_identifier=<package name>`,
   `algorithm=ES256` and `public_key_jwk`, then sign the returned `client_data` (section 5) and
   attempt enrollment with `client_data` and `signature`.
3. If any step fails, delete the new key.
4. On success, save a record: `id`, `app_identifier`, `created_at` and `updated_at` from the server
   response, plus `local_key_id`, `user_id`, the normalized `identifier_hint` and `policy`.
5. If saving throws, revoke the new credential on the server, delete the new key and fail.
6. Then delete every other local credential for the same `app_identifier` and `user_id`
   (best-effort), since the server keeps only one active credential for this client and app.
   Records for other users are left for reconciliation (4.1 step 8).

## 5. Signing format

- Sign the exact `client_data` string returned by the server, as UTF-8 bytes, with
  `SHA256withECDSA`. Do not decode or re-serialize it.
- Convert the DER signature to raw `r || s`: each integer is stripped of leading zero bytes and
  left-padded to 32 bytes, giving 64 bytes.
- Encode with unpadded base64url (`Base64.URL_SAFE | NO_PADDING | NO_WRAP`).
- Send `algorithm=ES256` alongside it.

Public key JWK sent at enrollment (coordinates are 32-byte big-endian, unpadded base64url):

```json
{"kty":"EC","crv":"P-256","x":"<x>","y":"<y>","alg":"ES256"}
```

## 6. Compatibility rules

- Any SDK that stores biometric credentials inside an app that may also contain `clerk-android`
  MUST use the identifiers, cipher and JSON schema in this document.
- Records and keys are shared. An SDK may use, replace or delete a credential that another SDK
  enrolled, following the rules in section 4.
- Changing any identifier, the value encoding or the meaning of a field requires bumping the
  contract version (and the `clerk:vN:` prefix where the encoding changes) and shipping a migration
  that reads v1. Because `clerk-android` drops unknown fields and treats unknown policies as
  `biometry_or_device_passcode`, adding a field or policy is also a breaking change.

## 7. Known limitations

- **Shared value-encryption key.** `clerk_preferences.master_key` also encrypts `DEVICE_TOKEN` (the
  client token) and other SDK state. Keystore keys are already scoped to the app's UID, so sharing
  the alias does not give code in the app any access it did not have, but an SDK implementing this
  contract can decrypt all of `clerk_preferences`. A credential-scoped key would need a v2.
- **Key creation race.** Two SDKs generating `clerk_preferences.master_key` at the same time can
  leave values encrypted with a key that was replaced. `clerk-android` deletes values it cannot
  decrypt, which would include `DEVICE_TOKEN`. SDKs should avoid writing before `clerk-android` has
  initialized when both are present.
- **No cross-SDK locking.** Both SDKs rewrite the whole `TRUSTED_DEVICE_CREDENTIALS` array.
  Concurrent writes from different SDKs can lose an update.
- **Silent save failures.** `clerk-android` logs and skips a write when the Keystore is unavailable
  or encryption fails. Enrollment then succeeds without a local record, and the revoke-on-failure
  path in 4.3 step 5 does not run.
- **Test coverage.** Robolectric has no `AndroidKeyStore`. The contract test installs an in-memory
  `AndroidKeyStore` JCA provider, so the production `AndroidKeystoreStorageCipher` and its key
  generation parameters run unmodified, but actual Keystore hardware behavior (IV generation, key
  size default) is not exercised.
