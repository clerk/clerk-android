# Android token freshness assertion audit

All ten declarations, the JWT builder and teardown in `TokenFreshnessTest.kt` were reviewed against baseline `1ea9f97250e9e3b266b7fbcfe37d9373e4fc393f`, together with the removed `TokenFreshness` and `SessionTokensCache` implementations. That legacy test file is retired. The separate 25-declaration `SessionTokenFetcherTest.kt` is covered by the [token request audit](token-request-test-audit.md).

Token ordering belongs to `packages/clerk-js/src/core/tokenFreshness.ts`, `tokenCache.ts` and `resources/Session.ts`. The native generated methods delegate to those owners. The new major does not preserve the old private cache API or its different expiration and hydration rules.

## Assertion dispositions

| Legacy declaration | Current owner and evidence |
| --- | --- |
| `keeps token with higher origin issued at` | Shared `pickFreshestJwt` ranks `oiat` before `iat`. The source test checks the comparison; packaged `TokenFreshnessContractTest` checks both HTTP response orders with a higher-origin token whose `iat` is lower. Each forced caller receives its own response, while the next cached read and next minter request use the freshest token. |
| `uses issued at to break equal origin issued at` | Shared `pickFreshestJwt` tests both directions. Packaged `equalOriginUsesIssuedAtDespiteResponseOrder` resolves the higher-iat response before the stale response and checks both the cached token and subsequent minter input. |
| `replaces an expired existing token` | Intentional owner change: the shared comparator ranks claims; it does not inspect wall-clock expiration. Shared cache lookup/eviction handles expiry separately. Source `tokenCache` tests cover expired-entry removal and remaining TTL; packaged `TokenSnapshotTest.expiredSnapshotPreservesFresherMintInput` checks that expired tokens cannot satisfy a cached read and that the next mint retains the freshest claims baseline as input. This does not assert parity with the removed Kotlin helper's expiration-first comparison. |
| `accepts incoming token when organization changes` | Shared `shouldKeepExistingLastActiveToken` compares only matching session/organization contexts. Source `Session` test `an org-switch token minted with a lower oiat still replaces the previous org lastActiveToken` verifies the change, and explicit-organization cache tests verify separate entries. No Kotlin freshness comparison remains. |
| `keeps decodable existing token when incoming cannot be decoded` | The old helper silently selected its existing argument. The shared `Token` constructor decodes incoming JWTs and rejects malformed input instead. Executed generated token-decoding cases cover missing segments, invalid base64 and invalid JSON: the call fails, the malformed value is not returned, selection is preserved and the runtime remains usable. This is an explicit error-behavior change, not a silent fallback guarantee. |
| `malformed token does not match session context` | The private `TokenFreshness.matches` predicate is removed. The generated decoding checks above exercise malformed endpoint responses; no native boolean JWT-validation API is introduced. |
| `token without session id does not match session context` | The private `matches` predicate is removed. Source `tokenSid` tests assert that a missing claim reads as undefined, and source cache tests prevent broadcasts without a session ID. These are not a promise that `Session.getToken` rejects every structurally valid server token without `sid`; the new API follows canonical resource/token handling rather than adding native JWT validation. |
| `cache cannot be rolled back by a stale response` | Shared cache monotonicity tests and both packaged response orders verify that a stale result cannot replace the cached winner. Each packaged case then returns an identical fresh token from a third forced request and checks a subsequent cached read without another HTTP request. The removed `didChangeCanonicalToken` flag has no generated public equivalent. |
| `out of order cache writes retain the freshest response` | The new packaged tests suspend two actual host HTTP responses, release them in each order, and check generated return values, cached reads, exact request count, stable selected-session handle and the next minter's previous-token field. They do not call a native cache helper. |
| `hydration preserves canonical token on a timestamp tie` | Intentional change: shared policy accepts the incoming token on a complete `oiat`/`iat` tie because other claims may differ. Existing packaged `timestampTieAcceptsIncomingSnapshot` checks the snapshot result; `mintedTimestampTieRemainsCached` checks the minted result. Both were executed for this audit. |

## Verification

The three new ordering cases pass against packaged QuickJS on the API 36 ARM64 emulator. All seven existing snapshot cases also pass in a separate run. The first attempted comma-separated class selector executed only the first class; its successful Gradle exit was not counted as snapshot evidence. Exact case names and results are retained under [evidence/token-freshness](evidence/token-freshness/proof.json).

The same JavaScript revision passes 200 focused source tests across `Session`, `tokenCache` and `tokenFreshness`, plus 26 generated embedded tests across token snapshots, decoding, request policy, invalidation and cancellation. The shared runtime, generated API and packaged bundle are unchanged by this audit. These fixtures do not establish live server token acceptance, physical-device lifecycle behavior or old-major signed-in upgrades.
