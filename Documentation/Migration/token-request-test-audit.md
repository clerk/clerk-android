# Android token request migration

The generated `Session.getToken` returns a token string or a canonical null result and throws `CoreException` on failure. It does not preserve the old fetcher's blanket null-on-error behavior, native expiration-buffer option, or error-code-driven local sign-out. A 401 triggers shared client recovery; the recovered client determines session selection. A pending session uses the canonical resource method and server outcome, with pending tasks still represented in state.

All 25 declarations and complete fixture/mock bodies in baseline `SessionTokenFetcherTest.kt` were reviewed together with `SessionTokenFetcher`, its options/cache-key extension, and the separately audited freshness/cache helpers. The old test file is retired. The immutable baseline remains `1ea9f97250e9e3b266b7fbcfe37d9373e4fc393f`; exact names and file hash remain in `legacy-tests.json` and the retained proof.

## Late host response fix

The new closing-owner test reproduced an uncaught `CoreException` from `QuickJSTransport.send`: after the runtime closed, a fixture HTTP capability completed a noncancellable wait and the host coroutine still tried to send its reply to the closed worker. Instrumentation stopped after nine of the then-eleven cases. This was a transport bug, not a token-cache bug.

The transport now sends a host reply only while its coroutine is active and closure has not started. The forced-call and coalesced-waiter cases verify that in-flight callers receive `runtime_disposed`, a late response cannot save its replacement credential, and later calls on the invalidated resource fail with `stale_resource`. The iOS transport already checks `Task.isCancelled` before sending a reply; this correction changes Android only. The shared TypeScript bundle and generated public signatures are unchanged.

An intermediate test failure came from accelerating every host timer: that also expired a recovered cache entry immediately. The fixture now accelerates only retry-sized delays while its HTTP failure is active. This does not change SDK retry or token-expiry policy.

## Verification and CI

`bash scripts/run-token-request-contract.sh` runs the packaged twelve-case suite and then requires all exact case names to pass, with no missing, duplicate, failed or skipped cases. The API 36 CI job runs this gate alongside the generated-core, platform and rendered-auth checks; it preserves earlier platform XML before the token run replaces the output directory.

The audit also uses the existing five packaged cancellation scenarios, eleven general packaged-core scenarios, three token-ordering scenarios and seven snapshot scenarios. Focused generated embedded token/session tests pass 43 cases on the unchanged JavaScript revision. The [freshness proof](evidence/token-freshness/proof.json) records 200 focused shared Session/cache/freshness tests on that same revision. Current native execution results and the reproduced failure are retained in [the token-request proof](evidence/token-requests/proof.json).

These are deterministic host-fixture checks. They do not establish live server authentication, actual old-major signed-in upgrades, or physical-device lifecycle and credential prompts.
