# Android arm64 App Bundle delivery measurement

Measured on 2026-09-09 from the paired `core-footprint` release App Bundles.
The harness and native artifact inputs are from `8d7d139e`; the generated core
revision remains `617418e19cd985de98333a5df3c8ab3b2d360190`. The measurement adds
build-time tooling without changing application dependencies or source behavior.

The actual emulator device specification was captured by bundletool:
Android API 36, arm64-v8a, 480 dpi, en-US. The complete specification, core and
contract hashes, App Bundle hashes, split APK hashes and download estimates are
in the [download report](android-arm64-bundle-download.json).

| Measurement | Baseline | Embedded core | Increase |
| --- | ---: | ---: | ---: |
| Estimated compressed download bytes | 58,530 | 1,573,733 | 1,515,203 |
| Installed app bytes after fresh split install | 172,032 | 3,190,784 | 3,018,752 |
| App data bytes | 57,344 | 57,344 | 0 |
| Cache bytes (included in app data) | 32,768 | 32,768 | 0 |

The incremental download estimate is 1.45 MiB against the 5 MiB budget. The
installed delta is 2.88 MiB against the 8 MiB budget. Both fit for this recorded
configuration. These are separate from the earlier monolithic-APK measurement;
APK gzip, bundletool delivery estimates and Android installed counters measure
different things.

## Method and execution

The pinned bundletool 1.18.3 `build-apks` command generated device-targeted sets.
The baseline has one base split. The embedded application has base, arm64, English
and xxhdpi splits. `get-size total --device-spec` returned identical minimum and
maximum values for this configuration. This is the compressed-delivery estimate
described in [Android's bundletool documentation](https://developer.android.com/tools/bundletool#measure_the_estimated_download_sizes_of_apks_in_an_apk_set), not an observed Play network transfer.

The same inputs generated byte-identical APK sets and individual splits on
repeated runs. The machine report records the actual bundletool and AAPT2 versions.
Arguments are passed through JSON arrays to the isolated Gradle JavaExec task;
the tool dependency is not part of either application's runtime classpath.

Both dedicated measurement apps were freshly installed using `install-apks`.
Each reached its ready marker. The embedded app executed packaged QuickJS,
connected the actual Clerk core through fixture HTTP/storage, called generated
`signIn.reset()` and checked nested-group invalidation. The native platform-host
branch remains reachable in the shrunk application but was not executed.

[Raw installed counters](android-arm64-bundle-install.json) come from each
application's own `StorageStatsManager.queryStatsForUid` call after ready. APK-set
hashes link those counters to the split artifacts. Both apps were force-stopped
after collection. No account, browser prompt or external service was involved.

## Limits and tooling correction

This validates split packaging and execution for one arm64 emulator configuration.
It does not establish physical-device startup/memory, other ABIs, real-account
upgrade continuity, iOS application size, or the footprint of prebuilt Compose UI.
An actual Play transfer can differ from a local estimate and was not performed.

The first device-spec command failed with
`NoClassDefFoundError: kotlin/jvm/internal/Intrinsics`: the standalone Maven
bundletool process lacked Kotlin runtime classes used by its shaded Android
libraries. The build-only configuration now explicitly supplies Kotlin stdlib.
The apps' dependency graphs were not changed. AAPT2 prints its version to stderr;
the report reader accepts either output stream and rejects a missing version.
